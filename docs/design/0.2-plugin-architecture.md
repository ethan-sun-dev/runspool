# RunSpool 0.2 设计：从底层开始的插件架构

> 状态：**已定稿**（2026-10-04），M1 实施中。中文审阅稿；正式文档出英文版。
> 参考：DeepSeek Harness（dsh）及其插件框架 Cordis 的核心思想，见文末「参考与署名」。
> 术语：「下游应用」指基于 RunSpool 构建的应用；「早期分叉」指某个下游应用里自带、独立演化过的一份引擎副本，本次改版把它的通用改进收回了 RunSpool。

## 1. 目标与非目标

**目标**

1. **一切皆插件。** 内核只认识「插件、服务、事件、生命周期」，不认识任务、步骤、数据库。任务存储、状态机、调度、命令行、审批、凭证，全部以插件形式装进来。内置能力和第三方插件用的是同一套机制，没有后门。
2. **守住 0.1 的可靠性不变量**（见 §5）。插件化不能以牺牲「崩溃不丢、状态不乱、步骤不重跑」为代价。
3. **插件是普通的 pip 包。** 通过 entry point 被发现，带版本兼容检查。
4. **应用 = 发行组合**：选一组插件、写一份配置。作者自己的两个下游应用（一个视频流水线、一个自媒体工具）都是这样的组合，不 fork 引擎。
5. **自带官方插件**：`runspool-wechat`（真实可用的公众号插件），以及几个示例插件。

**非目标（0.2 不做）**

- 热重载、运行时增删插件。插件集合只在启动和停机时变化；机制本身完整，但不对外开放运行时热插拔。
- 同一进程里并存两套同名服务（Cordis 的 `isolate`）。需要两套配置就跑两个进程。
- 异步内核。内核同步、单线程管生命周期；只有步骤在工作线程里跑。
- 插件沙箱。插件是受信任的 Python 代码，版本检查不是安全边界。
- 分布式、多机、Web UI、多租户。

## 2. 总体分层

```
┌─ 应用（发行组合）──────────────────────────────────────────┐
│  下游应用：profile + 私有插件包      │
├─ 官方插件（独立 pip 包，RunSpool 仓库 plugins/ 下）─────────────┤
│  runspool-wechat · runspool-example-*                            │
├─ 核心插件（随 runspool 发布，由 core bundle 默认装载）───────────┤
│  store-sqlite* · tasks · steps · workflows · runner · scheduler  │
│  daemon · approval* · credentials-local* · cli · doctor · views  │
│  builtin-steps（ingest_file / archive …，可禁用、可替换）         │
├─ 内核 runspool.kernel（约 500 行，零业务知识）──────────────────┤
│  Context · Fiber（生命周期 + 依赖注入）· Effect · Events          │
│  Compose（条目 / 补丁 / profile）· Loader（发现 / 兼容 / 启动审计）│
└──────────────────────────────────────────────────────────────┘
* 可替换的「接缝」（seam）：有契约、有一致性测试，任何实现通过测试即可替换。
```

服务分三类，借鉴 dsh 的划分：

| 类别 | 含义 | 例子 |
|---|---|---|
| **core** | 承载不变量，唯一实现，不可替换；只能通过事件观察或否决 | `tasks`（状态机）、`runner`、`steps` |
| **seam** | 契约固定、实现可换；实现必须通过一致性测试 | `store`、`approval`、`credentials` |
| **contribution** | 插件往 core 服务里登记的东西 | 步骤、工作流、命令、doctor 检查、维护钩子 |

## 3. 内核

内核移植的是 Cordis 的**思想**，用 Python 重写并做了简化（§1 的非目标）。

### 3.1 插件的形状

```python
class WechatConfig(BaseModel):          # 每个插件自带 pydantic 配置模型
    appid: str
    appsecret: CredentialRef = "WECHAT_APPSECRET"   # 只存凭证名，不存值

plugin = Plugin(
    name="wechat",
    Config=WechatConfig,                # 装载前校验并填默认值；不合法 → 插件 FAILED
    inject=["steps", "workflows", "credentials", "approval", "cli"],
    apply=apply,
)

def apply(ctx: Context, config: WechatConfig) -> None:
    ctx.steps.register(WechatDraftStep, factory=lambda: WechatDraftStep(config, ctx.credentials))
    ctx.workflows.provide_default("wechat_article", ["wechat_render", "wechat_draft"])
    ctx.cli.register(wechat_commands)
    ctx.doctor.register(check_wechat_credentials)
    ctx.on("step/pre-execute", require_approval_for_drafts)
```

- 插件可以是函数、类或带 `apply` 的对象（同 Cordis）。
- `apply` 里做的每一件登记都是一个 **effect**：自动记录撤销函数，插件卸载或装载失败时按逆序全部撤销。插件作者不用自己写清理代码。
- `inject` 声明依赖的服务。**没声明的服务拿不到**（访问即报错），依赖关系因此是显式的、可审计的。

### 3.2 服务与依赖注入

- `ctx.provide(name, value)` 提供服务；同名重复提供直接报错，不允许静默覆盖。
- 插件在 `inject` 的服务**全部就绪（提供者已 ACTIVE）**之前保持 PENDING，就绪后自动装载。所以插件的书写和登记顺序无关紧要。
- 提供者变了（换实现、卸载、原地重载），依赖它的插件自动卸载再按新提供者重装（借鉴 Cordis 的 epoch 机制；这里的依赖指纹是**每次服务注册的序号**，而不是提供者 fiber 的编号，所以提供者原地重载也会让依赖方重装、让之前失败的依赖方重试）。0.2 只在启动时用到这个机制，但实现是完整的。
- 服务可用的条件：提供者及其所有祖先插件都已 ACTIVE；例外是插件自己和它的后代，可以使用正在装载中的祖先已经提供的服务。
- 在插件装载或卸载过程中对它调用 dispose（比如在自己的 `apply` 里），会推迟到这次装载或卸载结束再执行，不会丢失。
- 生命周期：`PENDING → LOADING → ACTIVE`，或 `FAILED`（`apply` 抛异常或配置不合法，已登记的 effect 全部回滚，不影响其他插件），或 `UNLOADING → DISPOSED`。

### 3.3 事件

三种分发模式，按用途选（内核是同步的，Cordis 的 `serial` 即异步版 `bail`，不单列）：

| 模式 | 语义 | RunSpool 里的用途 |
|---|---|---|
| `emit` | 广播，忽略返回值；监听器异常被隔离并记日志 | `task/transitioned`（通知类插件）、`daemon/tick`（维护钩子） |
| `bail` | 依次调用，第一个非空返回即终止 | `task/before-transition`（只能否决，不能改目标状态） |
| `waterfall` | 洋葱式中间件 `(args…, next)`，不调用 `next()` 即否决 | `step/pre-execute`（审批、策略） |

Cordis 的 `emit` 会把监听器异常抛给发送方；我们改为**隔离**：观察者出错不能拖垮状态机提交。

### 3.4 组合：条目、补丁、profile

借鉴 dsh 的 bundle/profile 分层：

- **条目（entry）**：`{id, plugin, config, disabled}`。`id` 是稳定身份。
- **bundle**：一个 pip 包附带的一份补丁文件，声明「装哪些条目、默认配置是什么」。`runspool` 自带 `core` 和 `builtin-steps` 两个 bundle。
- **profile**：一个应用的配置文件 `runspool.yaml`，列出 bundle，再加自己的补丁。
- **叠加顺序**：各 bundle 的补丁（按 profile 列出的顺序）→ profile 自己的补丁 → 用户目录补丁 → 命令行 `--patch`。后者覆盖前者。
- 补丁动词：`insert` 新增条目；按 `id` 修改字段；`disabled: true` 停用（没有「删除」）。比如某个应用停用内置的 `archive`，换成自己的。
- `runspool config dump` 打印叠加后的最终结果，和启动时用的是同一个函数，不会不一致。

```yaml
# 某个下游应用的 runspool.yaml（示意）
bundles: [core, builtin-steps, myapp]
patch:
  - id: builtin-archive
    disabled: true
  - id: wechat
    config: { appid: wx123, theme: indigo }
workflows:
  default: [fetch, render, publish_draft, archive]
```

### 3.5 发现、兼容检查、启动审计

- **发现**：`importlib.metadata.entry_points(group="runspool.plugins")` 和 `group="runspool.bundles"`。
- **兼容**：插件包在 `Requires-Dist` 里声明 `runspool>=0.2,<0.3`，装载前用 `packaging` 检查；不兼容的条目标为停用并给出原因。确需强行使用，在 profile 里按 `包名@版本` 精确豁免。
- **启动审计**（dsh 踩过的坑：缺依赖时插件会**静默**卡在 PENDING）：启动后列出所有 PENDING 插件及其缺失的服务、所有 FAILED 插件及其错误。profile 声明的「必需条目」任一不是 ACTIVE，启动失败、非零退出。`runspool doctor` 同样输出这份报告。
- **核心条目不可关闭**：`steps`、`workflows`、`tasks`、`runtime`、`doctor` 承载不变量，profile 禁用它们或漏掉 `core` bundle 都会启动失败；`store` 是接缝，可以停用后换成别的实现，但必须有插件提供它。
- **读命令与运行命令的门槛不同**：`status`、`inspect` 这类只读命令容忍可选插件失败；`run` 和 `daemon` 要求**所有已启用插件都处于 ACTIVE**、所有懒加载步骤都能导入，否则拒绝启动。失败的插件可能本该提供或覆盖某个步骤，带病运行可能悄悄执行错误的步骤（M2 审查发现的真实案例）。不需要的插件请在 profile 里 `disabled: true`。
- 配置里声明的步骤（`steps:`）**懒加载**：启动时只占住名字（重名冲突当场发现），用到时才导入模块，所以只读命令不会导入用户步骤代码。

## 4. 核心插件

| 服务 | 类别 | 职责 | 由 0.1 的哪部分演变 |
|---|---|---|---|
| `store` | seam | 任务、事件、步骤记录的持久化原语：CAS 领取、带期望状态的原子迁移、按状态列表、白名单字段更新 | `persistence/repository`、`event_log`、`step_run_log`、`schema`、`connection` |
| `tasks` | core | **状态机，唯一的状态写入者**；暴露 claim/complete/defer/fail/pause/terminate/retry/wake/approve… | `persistence/state_machine` |
| `steps` | core | 步骤登记处；`register(step 或 factory) → 撤销函数` | `engine/registry`、`registry_builder` |
| `workflows` | core | 工作流定义（来自 profile 和插件默认值）+ 顺序校验器 | `config.workflows` |
| `runner` | core | 执行一步：构造 StepContext、跑 `step/pre-execute`、守卫、心跳、在步骤边界应用暂停/终止 | `engine/runner` |
| `scheduler` | core + 策略钩子 | 每个 tick 选任务、配额、到期重排、过期回收 | `engine/coordinator`、`worker_pool` |
| `daemon` | core | 常驻循环、pid、`daemon/tick` 维护钩子 | `daemon`、`runtime` |
| `approval` | seam | 审批服务（§6） | 新增 |
| `credentials` | seam | 凭证解析（§7） | 新增 |
| `cli` | core | typer 根命令；插件 `register` 子命令 | `cli`、`commands` |
| `doctor` | core | 检查项登记处 + 启动审计报告 | `doctor` |
| `views` | core | `--json` 契约（`available_actions`、`suggested_next_action`）、表格显示（按显示宽度截断 CJK） | `views`、`display` |

`store` 是唯一可替换的持久化接缝。默认实现 `store-sqlite`。RunSpool 提供 `runspool.testing.store_contract`：一套一致性测试（并发领取只有一个赢家、迁移带期望状态、事件与状态同事务、WAL 下并发写入……），任何替代实现必须通过。

## 5. 不变量怎么守

| # | 不变量 | 插件化后的保护手段 |
|---|---|---|
| I1 | 状态只由状态机写 | `tasks` 是 core，不可替换；`store` 只提供「带期望状态的原子迁移」原语，不提供裸的状态写入。插件只能通过 `task/before-transition` 否决、通过 `task/transitioned` 观察 |
| I2 | 步骤不碰数据库 | **步骤拿不到 `ctx`**。步骤只收到 `StepContext`；需要的服务在构造时由插件注入（如凭证），内核拒绝把 `store`、`tasks` 暴露给步骤 |
| I3 | 原子领取，同一步不双跑 | 领取 = CAS + `claim_token`（合并 早期分叉 的修复）；runner 执行前校验令牌；写进 `store_contract` |
| I4 | 暂停/终止只在步骤边界生效，终止优先 | 在 `runner`（core）里实现，插件无法绕过 |
| I5 | 崩溃恢复：中断的步骤视为未完成，干净重跑 | 不变；审批授权只对一次尝试有效，重跑需重新审批 |
| I6 | 对外操作默认拒绝（fail-closed） | 审批服务缺席、策略为 `never`、应答方出错，一律视为拒绝；守卫只能拒绝、不能放行 |

## 6. 审批闸门

借鉴 dsh 的工具管线，但改成**不占用工作线程**的异步审批：

1. runner 领取任务后、执行步骤前，跑 `step/pre-execute` waterfall，结果是封闭词表：`Allow | Deny(原因) | Defer(原因, 延迟) | Ask(原因)`。其余任何返回值一律按 `Deny` 处理。
2. 然后跑守卫（`steps.guard(fn)`）：守卫只能返回拒绝原因，不能放行。插件登记顺序因此无法把一个拒绝变成允许。
3. `Ask`：任务迁移到新状态 **`awaiting_approval`**，释放领取，同一事务写入 `approval_asked` 事件。工作线程立即释放。
4. 应答渠道是 `approval/request` 的监听器，可以有多个：命令行 `runspool approve <id>` / `reject <id>`、日后的微信或邮件通知插件。
5. 批准：迁回 `queued`，带一次性授权，绑定到（任务、步骤、第几次尝试）；拒绝：迁到 `manual_required`。两种结果都写入 `approval_decided` 事件，与 `approval_asked` 成对，构成审计记录。
6. 策略 `ask | never`。`never` 在分发给应答方之前直接拒绝；适合 CI。

步骤声明自己是否有对外副作用（`side_effect = True`）。默认策略插件规定：有副作用的步骤先 `Ask`。公众号建草稿就是这样。

## 7. 凭证

- 配置里只写**凭证名**（`CredentialRef`，形如 `WECHAT_APPSECRET`），不写值。
- `credentials` 服务：`resolve(名) → 值和来源`；`describe(名) → 是否已配置、来源、是否可写`（不含值，可安全显示和传输）。
- 默认实现 `credentials-local` 的查找顺序：进程环境变量 → `~/.config/runspool/credentials.yaml`（仅本人可读）→ 工作区 `.env` → `~/.env`。
- 使用方每次操作都重新解析、不缓存，换凭证不用重启。值永远不进日志。
- `doctor` 用 `describe()` 报告缺哪些凭证。

## 8. 任务模型的变化

| 变化 | 来源 |
|---|---|
| 新状态 `partially_completed`（终态）、`awaiting_approval` | 早期分叉、§6 |
| `StepResult.degraded`；`step_runs` 增加 `note` 列，状态增加 `degraded`、`interrupted` | 早期分叉、0.1 |
| `StepContext.attempt` | 早期分叉 |
| `StepDeferred(reason, delay_seconds)` | 早期分叉 |
| `next_retry_at` 统一为「不早于此时」；新增 `wake` 动作 | 两边冲突的合并方案 |
| `claim_token` 并入原子领取 | 早期分叉 + 0.1 |
| 任务 `metadata`（JSON）和 `parent_task_id`；公开的建任务接口（子流程用） | 下游需求 |
| 新库可指定任务编号起点 | 下游迁移需求 |
| 引入 schema 版本表和迁移框架（`store` 负责） | 新增 |

0.1 的 Python API（`from runspool.engine.step import Step` 等）**不保留兼容层**：0.1 在 PyPI 上没有已知外部用户，现有的两个应用会随这次改版一起迁移。CHANGELOG 写清楚破坏性变化。

## 9. 仓库与包的组织

RunSpool 仓库改为 uv workspace：

```
runspool/
  src/runspool/kernel/      内核
  src/runspool/core/        核心插件（随 runspool 一起发布）
  src/runspool/builtin/     内置步骤插件
  src/runspool/testing/     store_contract 等测试工具（给插件作者用）
  plugins/runspool-wechat/  官方插件：公众号
  plugins/runspool-example-file-pipeline/   示例插件（由现有 examples 改写）
  plugins/runspool-example-creator/
  THIRD_PARTY_NOTICES.md
```

- `runspool`（内核 + 核心插件 + 内置步骤）是一个 pip 包，装上即可运行。
- 每个官方插件是独立的 pip 包，各自发布到 PyPI。
- `scripts/check-downstream.sh`：推送前跑下游应用的测试。

## 11. 实施顺序

每个里程碑独立分支，测试全绿再合并。

| 里程碑 | 内容 | 完成标准 |
|---|---|---|
| M1 内核 | Context、Fiber、Effect、Events、Compose、Loader、启动审计 | 内核单元测试覆盖生命周期、依赖注入、回滚、补丁叠加、兼容检查 |
